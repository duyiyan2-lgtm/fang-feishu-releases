# 仿飞书协同办公平台 10 天 MVP 项目方案

> 团队配置：4 个开发，2 个运维。  
> 周期：10 天。  
> 目标：完成一个可运行、可演示、可部署、文档完整的仿飞书协同办公平台 MVP。

## 一、总体策略

10 天时间不足以完成 README 中的全量飞书复刻，因此本项目采用 MVP 策略：

1. 只做 PC Web，不做 App、小程序、桌面端。
2. 只做核心业务闭环，不做复杂增强能力。
3. 开发组专注功能实现，运维组专注环境、部署、测试、文档和验收。
4. Day 5 必须完成中期可演示版本，Day 8 必须跑通完整主流程，Day 10 完成验收。

## 二、功能范围

### 1. 必做功能

| 模块 | 实现范围 | 验收标准 |
| :-- | :-- | :-- |
| 用户中心 | 登录、退出、JWT 鉴权、当前用户信息 | 用户可登录，接口有权限控制 |
| 管理后台 | 用户管理、部门管理、角色管理、操作日志 | 管理员可维护基础组织数据 |
| 通讯录 | 部门树、成员列表、成员搜索、员工名片 | 普通用户可查找同事 |
| 即时通讯 | 单聊、群聊、历史消息、未读数、撤回 | 两个用户可实时收发消息 |
| 协同文档 | 文档列表、创建、编辑、保存、评论 | 用户可创建并编辑文档 |
| 云盘 | 文件上传、下载、列表、删除 | 用户可上传和下载文件 |
| 消息通知 | 站内通知、未读提醒 | 聊天、审批等操作产生通知 |
| 部署交付 | Docker Compose、Nginx、数据库初始化 | 可在本地或服务器启动演示环境 |
| 文档测试 | 需求、接口、数据库、测试、部署、日报 | 有完整验收材料 |

### 2. 简化功能

| 模块 | 简化实现 |
| :-- | :-- |
| 日历 | 只做日程新增、查询、编辑、删除 |
| 审批 | 只做请假审批：提交、通过、驳回 |
| 应用中心 | 只做静态应用入口展示 |

### 3. 暂不实现

| 模块 | 原因 |
| :-- | :-- |
| 视频会议 | 音视频、录制、屏幕共享复杂度过高 |
| 多端 App / 小程序 / 桌面端 | 10 天内无法稳定交付 |
| SSO / 三方登录 | 依赖外部平台配置 |
| OpenAPI / Webhook | 放到二期，当前只保留 Swagger |
| Elasticsearch | 先用数据库查询替代 |

### 2. 分工原则

| 方向 | 工作重点 |
| :-- | :-- |
| 4 个开发 | 保证登录、通讯录、IM、文档、云盘、后台这些功能能用 |

## 八、最小验收路线

最终演示按以下顺序进行：

1. 管理员登录。
2. 管理员创建部门、角色、用户。
3. 普通用户登录。
4. 查看通讯录并搜索同事。
5. 用户 A 和用户 B 进行实时聊天。
6. 用户 A 创建文档并保存。
7. 用户 B 打开文档并评论。
8. 用户 A 上传文件到云盘并下载。
9. 用户 A 创建日程。
10. 用户 A 提交请假审批。
11. 管理员审批通过。
12. 管理员查看操作日志。
13. 展示 Swagger 接口文档。
14. 展示 Docker 部署文档、测试报告和项目文档。

## 九、风险控制

| 风险 | 应对 |
| :-- | :-- |
| 开发只有 4 人，功能多 | 只保留核心业务闭环，复杂能力全部后置 |
| 运维被动等待 | 运维从 Day 1 介入环境、数据、文档、测试 |
| IM 联调失败 | Day 4 必须完成最小单聊，否则取消群聊增强 |
| 文档来不及 | F 每天收集截图和说明，当天沉淀文档 |
| 部署不稳定 | E 固定 Docker Compose 和初始化脚本 |
| 前端页面过多 | 页面优先做可演示版本，样式统一但不追求精修 |
